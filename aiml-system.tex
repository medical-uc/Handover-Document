\subsection*{System Architecture}

\subsubsection*{Architectural Philosophy: The ``Two Halves'' Principle}

The system is strictly partitioned into two decoupled halves that interact exclusively through
persisted storage contracts:

\begin{itemize}
    \item \textbf{The Offline Content \& Knowledge Pipeline (Heavy AI/ML):}
    \begin{itemize}
        \item Ingests raw textbook PDFs and slides.
        \item Executes multimodal OCR, vision-language diagram parsing, rule-based AST
              transformations, scispaCy/SapBERT medical entity linking, and multi-step LLM
              question generation with self-critique.
        \item Requires CUDA/MPS GPU hardware, PyTorch, Transformers, FAISS, and isolated
              Python runtimes.
        \item Produces clean, validated relational tables in PostgreSQL (\texttt{mcq\_questions})
              and semantic graphs in Neo4j / RDF (\texttt{graph.nq}).
    \end{itemize}

    \item \textbf{The Live Serving Layer (FastAPI + iPadOS):}
    \begin{itemize}
        \item High-throughput, CPU-bound REST API built on FastAPI and Uvicorn.
        \item \textbf{Zero PyTorch or Transformers runtime dependencies} --- the serving layer
              never loads model weights, eliminating GPU hosting costs, cold-start latency, and
              out-of-memory crashes on web workers.
        \item Backed by PostgreSQL for immutable question content and Neo4j for event-sourced
              student interaction history, spaced repetition scheduling, and topic mastery.
        \item Real-time personalization executes directly on the student's iPad using an
              on-device Bayesian Knowledge Tracing (BKT) engine.
    \end{itemize}
\end{itemize}

\subsubsection*{Storage \& Graph Topology}

The persistence model leverages PostgreSQL for relational data and Neo4j for event-sourced
graph data.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\linewidth]{images/mermaid_graph_schema.pdf}
    \caption{Neo4j Student Knowledge Graph Schema: nodes, relationships, and property contracts.}
\end{figure}

Key graph design rules:

\begin{enumerate}
    \item \textbf{Event Sourcing:} Every student interaction creates an immutable
          \texttt{InteractionEvent} node linked in chronological order via \texttt{:NEXT} edges
          and grouped under \texttt{:QuizSession} / \texttt{:FlashcardSession} via
          \texttt{:HAS\_ANSWER}.
    \item \textbf{Mutable Schedules as Edges:} Spaced repetition schedules are stored directly
          on the \texttt{(Student)-[:REVIEWING]->(Question)} edge (quiz) and the
          \texttt{Flashcard} node (flashcards), updating deterministically upon each submission.
    \item \textbf{Mastery Persistence:} The \texttt{:MASTERS} edge represents the student's
          on-device BKT estimate ($p_{\text{know}}$), synchronised asynchronously via
          \texttt{PUT /quiz/mastery}.
    \item \textbf{Relational Question Isolation:} The \texttt{Question} node in Neo4j contains
          \textbf{only} \texttt{uid}. Stem text, options, explanations, and diagrams reside in
          PostgreSQL to protect graph traversal performance.
\end{enumerate}

\textbf{Why Opaque Bearer Tokens (Not JWT)?}

JWTs cannot be instantly revoked without a distributed blacklist. Storing a SHA-256 hashed
token in Neo4j allows instantaneous server-side revocation on logout
(\texttt{revoked\_at = datetime()}) while keeping raw tokens out of the database.

\subsection*{End-to-End Application Flows}

\subsubsection*{Flow 1: Complete System End-to-End Dataflow}

The application architecture coordinates three decoupled subsystems spanning offline content preparation, batch parameter estimation, and real-time interactive learning:

\begin{enumerate}
    \item \textbf{Offline Content Ingestion \& AI Generation:} Medical textbook PDFs are parsed via the MinerU CLI to extract bounding-box layouts and visual figures. Cleaned text (processed via an 8-stage rule-based AST engine) and multimodal figure captions (generated by \texttt{Qwen2.5-VL-7B-Instruct}) are unified into structured Markdown. Semantic chunking (\texttt{all-MiniLM-L6-v2}) feeds a 6-step LLM question generation pipeline (\texttt{Qwen3.5-27B} / \texttt{HuatuoGPT-o1-72B}), storing finalized questions in PostgreSQL (\texttt{mcq\_questions}).
    \item \textbf{Bayesian Knowledge Tracing (BKT) Parameter Training:} Student interaction events (\texttt{:QUIZ\_ANSWER}) recorded in Neo4j are pooled for global parameter fitting. The server executes the Baum-Welch Expectation-Maximisation (EM) algorithm (\texttt{src/quiz/bkt\_fit.py}) to update population-wide transition, slip, and guess probabilities, exposing them through \texttt{GET /quiz/mastery/params}.
    \item \textbf{Live Student Learning Interaction:} The iPadOS client authenticates with the FastAPI backend, caching session tokens in Keychain. Students engage with interactive Quiz and Flashcard modules with sub-15\,ms instant feedback, on-device Bayesian mastery updates, and asynchronous graph persistence to Neo4j.
\end{enumerate}

\subsubsection*{Flow 2: Student Authentication \& Session Lifecycle}

The iPadOS client manages student identity through an opaque Bearer token architecture:

\begin{enumerate}
    \item \textbf{Registration \& Login:} The student submits credentials via \texttt{POST /students/login} or \texttt{POST /students/register}. The backend matches or creates the \texttt{:Student} node in Neo4j, mints a 32-byte cryptographic token (\texttt{secrets.token\_urlsafe(32)}), computes its SHA-256 hash, and stores a \texttt{:Session} node with a 30-day expiration timestamp (\texttt{expires\_at}).
    \item \textbf{Secure Client Storage:} The raw token is returned to iPadOS and stored in \texttt{KeychainStore} using the Apple Security framework, while \texttt{SessionManager} publishes the active authentication state.
    \item \textbf{Middleware Verification:} Subsequent HTTP requests provide the token via the \texttt{Authorization:}\allowbreak\ \texttt{Bearer <token>} header. \texttt{SessionAuthMiddleware} intercepts requests, computes the SHA-256 hash, and performs a single Cypher lookup against Neo4j to confirm the session is unrevoked and unexpired, injecting \texttt{student\_id} into \texttt{request.state}.
\end{enumerate}

\subsubsection*{Flow 3: Quiz Execution, Grading \& Mastery Sync}

The quiz lifecycle operates across four sequential phases designed to deliver instant feedback while guaranteeing asynchronous persistence:

\begin{enumerate}
    \item \textbf{Option Selection \& Instant Grading:} The student selects an answer option and confidence level (\textit{Confident / Unsure / Guessing}). \texttt{POST /quiz/questions/\{uid\}/check} is a public, stateless endpoint that evaluates the option against an in-memory sanitized question bank---returning \texttt{correct}, \texttt{correct\_index}, and clinical \texttt{explanation} in sub-15\,ms.
    \item \textbf{On-Device BKT Update:} \texttt{BKTStore.record()} computes the Bayesian posterior mastery $p_{\text{know}}$ using confidence-stratified slip and guess probabilities. The updated estimate is written to local \texttt{UserDefaults} and synchronised to Neo4j via an asynchronous background \texttt{PUT /quiz/mastery} call.
    \item \textbf{Stateful Log Commit:} When navigating to the next question, the client issues an authenticated \texttt{POST /quiz/questions/\{uid\}/log} request. The backend commits an immutable \texttt{:QUIZ\_ANSWER} event linked to the active \texttt{:QuizSession} and updates the spaced-repetition schedule on the \texttt{(Student)-[:REVIEWING]->(Question)} edge.
    \item \textbf{Quiz Completion \& Gamification:} \texttt{POST /quiz/sessions/\{id\}/end} finalises the session, aggregates score metrics, updates the student's daily activity streak, and awards $+5$ Energy currency in Neo4j.
\end{enumerate}

\subsubsection*{Flow 4: Flashcard Spaced Repetition Lifecycle}

Flashcard study sessions employ a modified SuperMemo spaced repetition algorithm tailored to student knowledge state:

\begin{enumerate}
    \item \textbf{Deck Assembly \& Weakness Prioritisation:} When initiating a session via \texttt{POST /flashcards/sessions}, the backend queries due cards where $\texttt{next\_review\_at} \le \text{now}$. Any remaining slots in the batch are dynamically filled with cards corresponding to the student's lowest BKT mastery topics ($p_{\text{know}}$).
    \item \textbf{Card Front \& Answer Reveal:} The client presents the question stem and prompt. Tapping ``Reveal Answer'' dispatches \texttt{POST /flashcards/cards/\{uid\}/reveal} to retrieve the detailed answer back and explanation.
    \item \textbf{Recall Rating \& Interval Update:} The student evaluates recall quality on a 4-point scale (\textit{Again, Hard, Good, Easy}). \texttt{POST /flashcards/cards/\{uid\}/log} records a \texttt{:FLASHCARD\_REVIEW} node, recalculates interval days and repetition streaks on the \texttt{:Flashcard} node, awards $+1$ Energy, and returns the next review date.
\end{enumerate}

\subsubsection*{Flow 5: Adaptive Knowledge Tracing \& Personalization Loop}

The personalization engine implements a closed-loop hybrid architecture combining server-side population fitting with client-side real-time state tracking:

\begin{enumerate}
    \item \textbf{Server-Side Population Parameter Fitting (Periodic Batch):} Interaction sequences are extracted from pooled \texttt{:QUIZ\_ANSWER} nodes in Neo4j. The Baum-Welch EM script (\texttt{src/quiz/bkt\_fit.py}) executes Forward-Backward rescaling (E-step) and expectation maximisation (M-step) to derive global parameters: $p_{\text{init}}$, $p_{\text{transit}}$, and confidence-conditioned $p_{\text{slip}}(c)$ and $p_{\text{guess}}(c)$. Fitted parameters are cached and exposed via \texttt{GET /quiz/mastery/params}.
    \item \textbf{Client-Side Real-Time Knowledge Tracing (iPadOS):} On application launch, \texttt{BKTStore} refreshes and caches population parameters. When the student answers a question with confidence $c$, \texttt{BKTStore} computes the closed-form Bayesian posterior:
    \begin{equation}
        p(L_t \mid y_t, c) = \frac{p(L_{t-1}) \cdot P(y_t \mid L_t, c)}{P(y_t \mid c)}
    \end{equation}
    and applies the transition prior $p(L_{t+1}) = p(L_t \mid y_t, c) + (1 - p(L_t \mid y_t, c)) p_{\text{transit}}$. The resulting $p_{\text{know}}$ is stored in local storage and dispatched asynchronously to Neo4j via \texttt{PUT /quiz/mastery}.
    \item \textbf{Downstream Personalization Delivery:}
    \begin{itemize}[leftmargin=*]
        \item \textit{Weighted Quiz Selection:} Multi-topic quizzes sample questions with weights inversely proportional to topic mastery ($\propto 1 - p_{\text{know}}$).
        \item \textit{Flashcard Weak-Topic Infill:} Practice decks prioritize review cards from topics exhibiting the lowest mastery scores.
        \item \textit{Adaptive Nudges \& Progress:} The backend \texttt{GET /students/me/nudge} endpoint inspects \texttt{:MASTERS} edges to surface high-priority study recommendations on the dashboard, while \texttt{SubjectsView} renders real-time topic progress bars.
    \end{itemize}
\end{enumerate}

\subsubsection*{Flow 6: Offline Multimodal Ingestion \& MCQ Generation Pipeline}

The offline ingestion pipeline converts unstructured medical textbooks into validated, high-yield multiple-choice questions across five sequential stages:

\begin{enumerate}
    \item \textbf{Stage 1: Parsing \& Normalization:} The MinerU CLI (isolated in a Python 3.10 virtual environment, \texttt{.venv-mineru}) processes textbook PDFs to extract layout bounding boxes (\texttt{\_middle.json}) and crop embedded anatomical figures and diagrams (\texttt{images/*.jpg}).
    \item \textbf{Stage 2: 8-Stage Post-Processing Engine (\texttt{src/post\_process}):} Performs deterministic schema validation, layout block flattening, typographic/geometrical feature extraction, header/footer repetition filtering, rule-based block classification (Title, Section, Paragraph, Table), cross-page reading order reconstruction, and semantic tree construction (\texttt{\_post\_processed.json}).
    \item \textbf{Stage 3: Multimodal Captioning \& Semantic Chunking:} \texttt{Qwen2.5-VL-7B-Instruct} generates detailed descriptions and clinical transcriptions for visual crops. \texttt{unify.py} merges textual AST and visual captions into unified Markdown, which is segmented into context-enriched chunks (\texttt{\_v1\_chunks.json}) via \texttt{all-MiniLM-L6-v2} semantic boundary embeddings.
    \item \textbf{Stage 4: 6-Step LLM MCQ Generation (\texttt{notebooks/mcq\_generation.ipynb}):}
    \begin{itemize}[leftmargin=*]
        \item \textit{Step 1 (Chunk Filtering):} Prepends hierarchical context headings to each chunk.
        \item \textit{Step 2 (Triple Extraction):} Uses \texttt{Qwen3.5-27B} / \texttt{HuatuoGPT-o1-72B} to extract biomedical triples over 13 core clinical relations.
        \item \textit{Step 3 (Distractor Synthesis):} Employs a two-tier strategy retrieving in-corpus medical entities with LLM fallback generation.
        \item \textit{Step 4 (Stem Generation):} Constructs question stems across Recall, Application, and Clinical Vignette modalities.
        \item \textit{Step 5 (Self-Critique):} Executes a 1-cycle verification prompt checking factual accuracy and key uniqueness, applying minimal-edit repairs.
        \item \textit{Step 6 (Option Shuffling \& UID Generation):} Shuffles options and serializes to \texttt{question\_\allowbreak bank.json}.
    \end{itemize}
    \item \textbf{Stage 5: Database Population:} \texttt{scripts/populate\_mcq\_postgres.py} ingests validated questions, distractors, and explanations directly into the PostgreSQL \texttt{mcq\_questions} table.
\end{enumerate}

\subsubsection*{Flow 7: Domain Knowledge Graph (medkg) Pipeline}

The domain knowledge graph pipeline constructs a formal, ontology-grounded biomedical semantic graph across eight stages:

\begin{enumerate}
    \item \textbf{Stage 1 (Parse):} Ingests semantically tagged Markdown containing clinical inline annotations (\texttt{<con>}, \texttt{<def>}, \texttt{<clin>}), validating and normalizing character spans.
    \item \textbf{Stage 2 (Extract):} Performs Named Entity Recognition via \texttt{scispaCy} (\texttt{en\_core\_\allowbreak sci\_scibert}) and biomedical relation extraction using \texttt{HuatuoGPT-o1-72B} over a 27-relation medical ontology.
    \item \textbf{Stage 3 (Link):} Maps extracted entity surface forms to standard UMLS/SNOMED CT Concept Unique Identifiers (CUIs) using \texttt{SapBERT} dense embeddings indexed in FAISS (\texttt{IndexFlatIP}, cosine similarity threshold $\ge 0.70$).
    \item \textbf{Stage 4 (Post-coordination):} Mints scoped \texttt{:INSTANCE} nodes to model complex clinical modifiers and qualifiers without combinatorial ontology explosion.
    \item \textbf{Stage 5 (Multimodal Grounding):} Connects visual figure captions and anatomical depictions to corresponding concept nodes.
    \item \textbf{Stage 6 (RDF Assertion):} Serializes extracted assertions into W3C RDF Named Quads (\texttt{<subject> <predicate> <object> <graph>}) with provenance metadata.
    \item \textbf{Stage 7 (OWL-RL Reasoning):} Applies deterministic OWL 2 RL inference rules to materialize implicit taxonomic, inverse, and transitive relationships.
    \item \textbf{Stage 8 (Serving):} Exports the reasoned knowledge base as N-Quads, hosts a SPARQL query endpoint, and synchronises triples into Neo4j via Neosemantics (\texttt{n10s}) to empower graph-grounded MCQ generation and semantic exploration.
\end{enumerate}

\subsubsection*{Zero-Inference Live Serving Architecture}

A critical architectural achievement is that \textbf{the live FastAPI serving application
performs zero model inference at runtime}:

\begin{enumerate}
    \item \textbf{CPU-Only Bound:} The production server requires only standard CPU instances
          (e.g.\ 2 vCPUs, 4\,GB RAM) with negligible footprint.
    \item \textbf{Instant Latency:} Response times for \texttt{/quiz/questions},
          \texttt{/quiz/check}, and \texttt{/quiz/log} remain sub-15\,ms because they execute
          indexed PostgreSQL queries and atomic Cypher graph transactions without model queue
          delays.
    \item \textbf{High Reliability:} Server stability is completely decoupled from GPU drivers,
          CUDA version mismatches, or VRAM exhaustion.
\end{enumerate}

\subsubsection*{Multi-Environment Isolation Strategy}

Because several specialised medical AI libraries carry incompatible Python and C-extension
dependencies, the project isolates runtimes into three dedicated virtual environments:

\begin{itemize}
    \item \textbf{\texttt{.venv/}} --- Main Environment: Python $\geq$ 3.13 (managed by
          \texttt{uv}). Dependencies: FastAPI, Uvicorn, Neo4j, SQLAlchemy, PyTorch,
          Transformers, Accelerate, Pydantic, SlowAPI.
    \item \textbf{\texttt{.venv-mineru/}} --- Isolated Environment: Python 3.10/3.11.
          Dependencies: \texttt{mineru}, \texttt{magic-pdf}, Detectron2, PaddlePaddle.
          Invoked exclusively as a subprocess from \texttt{scripts/\allowbreak ingest\_\allowbreak data.py}.
    \item \textbf{Domain KG env} --- Isolated Environment: Python 3.9--3.11.
          Dependencies: scispaCy, spacy\,$<$\,3.8, faiss-cpu, rdflib, owlrl.
          Required for Stage 2 NER and Stage 3 UMLS linking.
\end{itemize}

\subsubsection*{Hardware Optimisation \& Native Runtime Guards}

\begin{itemize}
    \item \textbf{Dynamic Device Selection with MPS Bug Workarounds}\\
          (\texttt{src/\allowbreak captioning/\allowbreak qwen\_vl.py}):
          {\sloppy Dynamically allocates execution targets (CUDA $\to$ MPS $\to$ CPU) and implements
          explicit memory purging (\texttt{torch.mps.\allowbreak empty\_cache()},\allowbreak\ \texttt{gc.\allowbreak collect()})
          upon completion to operate smoothly within Apple Silicon Unified Memory constraints.\par}

    \item \textbf{Native macOS Segfault Protection (\texttt{src/\allowbreak domain\_kg/\allowbreak native\_env.py}):}
          Addresses an issue on macOS where PyTorch, Thinc/Blis (spaCy), and FAISS clash when
          initialising separate OpenMP thread pools, resulting in \texttt{Segmentation fault: 11}.
          Setting \texttt{MEDKG\_NATIVE\_THREADS=1} and \texttt{KMP\_DUPLICATE\_LIB\_OK=TRUE}
          at the top of the package before any C-extensions load prevents segmentation crashes.
\end{itemize}

\subsection*{Mathematical Foundations \& Algorithms}

\subsubsection*{Bayesian Knowledge Tracing (BKT) with Confidence Emissions}

Standard BKT models a student's latent knowledge of a specific medical topic as a 2-state
Hidden Markov Model:

\begin{itemize}
    \item \textbf{State 0:} \textit{Doesn't Know}
    \item \textbf{State 1:} \textit{Knows}
\end{itemize}

To account for metacognitive awareness, emission probabilities $p_{\text{slip}}$ and
$p_{\text{guess}}$ are conditioned on the student's self-reported confidence
$c \in \{\text{confident},\,\text{unsure},\,\text{guessing}\}$:

\begin{center}
\begin{tabular}{|l|c|c|>{\raggedright\arraybackslash}p{0.48\linewidth}|}
\hline
\textbf{Confidence ($c$)} & $p_{\text{slip}}$ & $p_{\text{guess}}$ & \textbf{Pedagogical Interpretation} \\
\hline
\textbf{Confident} & $0.05$ & $0.10$ & Confident-wrong strongly penalises $p_{\text{know}}$ as a misconception. \\
\hline
\textbf{Unsure} & $0.10$ & $0.25$ & Standard baseline BKT behaviour. \\
\hline
\textbf{Guessing} & $0.30$ & $0.50$ & Correct guess does not falsely award mastery. \\
\hline
\end{tabular}
\end{center}

\textbf{Observation Update (Bayes Rule):} Given prior mastery $p_{\text{know}}$ and observation
$O_t \in \{\text{Correct},\,\text{Incorrect}\}$ with confidence $c$:

\[
O_t = \text{Correct}: \quad
p_{\text{know}}^{\text{post}} = \frac{p_{\text{know}} \cdot (1 - p_{\text{slip}}[c])}
  {p_{\text{know}} \cdot (1 - p_{\text{slip}}[c]) + (1 - p_{\text{know}}) \cdot p_{\text{guess}}[c]}
\]

\[
O_t = \text{Incorrect}: \quad
p_{\text{know}}^{\text{post}} = \frac{p_{\text{know}} \cdot p_{\text{slip}}[c]}
  {p_{\text{know}} \cdot p_{\text{slip}}[c] + (1 - p_{\text{know}}) \cdot (1 - p_{\text{guess}}[c])}
\]

\textbf{Learning State Transition} (accounting for knowledge acquisition during the attempt):
\[
p_{\text{know}}^{\text{next}} = p_{\text{know}}^{\text{post}} + (1 - p_{\text{know}}^{\text{post}}) \cdot p_{\text{transit}}
\]

\subsubsection*{Baum-Welch Expectation-Maximisation (EM) Parameter Fitting}

Implemented in \texttt{src/quiz/bkt\_fit.py}, the Baum-Welch EM algorithm fits optimal global
parameters across all pooled student sequences:

\begin{enumerate}
    \item \textbf{E-Step (Forward-Backward Rescaling):} Compute smoothed posterior state
          probabilities $\gamma_t(i) = P(S_t = i \mid \mathbf{O})$ and transition probabilities
          $\xi_t(0,1) = P(S_t = 0,\, S_{t+1} = 1 \mid \mathbf{O})$.
    \item \textbf{M-Step (Closed-Form Aggregation):}
\end{enumerate}

\[
p_{\text{init}} = \frac{1}{|\mathcal{S}|} \sum_{s \in \mathcal{S}} \gamma_0^{(s)}(1)
\qquad
p_{\text{transit}} = \frac{\sum_{s} \sum_{t} \xi_t^{(s)}(0,1)}{\sum_{s} \sum_{t} \gamma_t^{(s)}(0)}
\]

\[
\forall c:\;
p_{\text{slip}}[c] = 1 - \frac{\sum_{s} \sum_{t:\,O_t=\text{Correct},\,C_t=c} \gamma_t^{(s)}(1)}
  {\sum_{s} \sum_{t:\,C_t=c} \gamma_t^{(s)}(1)}
\qquad
p_{\text{guess}}[c] = \frac{\sum_{s} \sum_{t:\,O_t=\text{Correct},\,C_t=c} \gamma_t^{(s)}(0)}
  {\sum_{s} \sum_{t:\,C_t=c} \gamma_t^{(s)}(0)}
\]

\subsubsection*{Dual-Track Spaced Repetition Scheduling}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\linewidth]{images/mermaid_spaced_repetition.pdf}
    \caption{Dual-track spaced repetition: Quiz track (REVIEWING edge) and Flashcard track
             (SuperMemo self-rating intervals).}
\end{figure}

The two tracks use distinct scheduling mechanics:

\begin{itemize}
    \item \textbf{Quiz Track} (\texttt{(Student)-[:REVIEWING]->(Question)} edge): Correct +
          Confident $\Rightarrow$ \texttt{streak += 1}, \texttt{interval = min(60, interval$\times$2)}.
          Wrong or low-confidence $\Rightarrow$ reset: \texttt{streak = 0}, \texttt{interval = 1}.
    \item \textbf{Flashcard Track} (\texttt{Flashcard} node):
          \textit{Again} $\Rightarrow$ reset to 1 day;
          \textit{Hard} $\Rightarrow$ interval $\times$ 1.2;
          \textit{Good} $\Rightarrow$ streak $+1$, interval $\times$ 2.0;
          \textit{Easy} $\Rightarrow$ streak $+1$, interval $\times$ 2.5. All capped at 60 days.
\end{itemize}

\subsubsection*{Gamification Economy: Streaks, Energy \& Nudge Heuristics}

\begin{enumerate}
    \item \textbf{Consecutive Streak Tracking (\texttt{src/student\_kg/streak.py}):}
          Evaluates distinct calendar days in UTC where the student generated at least one
          \texttt{QUIZ\_ANSWER} or \texttt{FLASHCARD\_\allowbreak REVIEW}. A gap $\geq 2$ days resets
          \texttt{current\_streak = 0} while \texttt{previous\_streak} retains the broken length.
    \item \textbf{Streak Restoration (\texttt{POST /students/me/streak/restore}):}
          If the student missed exactly 1 day, they spend \textbf{10 Energy} units to bridge
          the gap and restore their previous streak.
    \item \textbf{Energy Ledger (\texttt{src/student\_kg/energy.py}):}
          Earned: $+5$ per Quiz Session completion, $+1$ per Flashcard Review.
          Spent: $-10$ per Streak Restore.
    \item \textbf{Nudge Recommendation Engine (\texttt{GET /students/me/nudge}):}
          Aggregates total due quiz questions and due flashcards, identifying the single item
          with $\min(\texttt{next\_review\_at})$ across both modes to populate the top
          dashboard reminder card.
\end{enumerate}

\subsection*{Developer Extension Guide \& Future Roadmap}

\subsubsection*{Recipe: Adding a New Backend Endpoint}

To expose a new API endpoint (e.g.\ \texttt{POST /students/me/bookmarks}):

\begin{enumerate}
    \item \textbf{Define Schema:} Add request/response Pydantic models to \texttt{app/schemas.py}.
    \item \textbf{Implement Domain Logic:} Add graph query functions in
          \texttt{src/student\_kg/}.
    \item \textbf{Register Router Route:} Add a route handler to
          \texttt{app/routers/students.py} specifying \texttt{@router.post(...)}.
    \item \textbf{Configure Auth Allowlist (If Public):} If unauthenticated, update regex rules
          in \texttt{app/auth\_middleware.py}.
    \item \textbf{Add Tests:} Create corresponding test cases in \texttt{tests/}.
\end{enumerate}

\subsubsection*{Recipe: Adding a New iPadOS Feature / View}

To implement a new feature view (e.g.\ \texttt{BookmarksView}):

{\sloppy
\begin{enumerate}
    \item \textbf{Declare Protocol Method:} Add the \texttt{async} API signature to
          \texttt{Core/\allowbreak Networking/\allowbreak APIClientProtocol.swift}.
    \item \textbf{Implement Network Call:} Implement the method in
          \texttt{Features/\allowbreak Bookmark/\allowbreak BookmarkAPI.swift}
          using \texttt{client.get(...)} or \texttt{client.send(...)}.
    \item \textbf{Build ViewModel:} Create \texttt{BookmarkViewModel} conforming to
          \texttt{ObservableObject} marked \texttt{@MainActor}, holding \texttt{@Published} state
          and injecting \texttt{any APIClientProtocol}.
    \item \textbf{Construct SwiftUI View:} Build the interface in
          \texttt{BookmarkView.swift} observing \texttt{BookmarkViewModel}.
    \item \textbf{Register Navigation:} Add an enum case to \texttt{SidebarItem} in
          \texttt{Core/\allowbreak UI/\allowbreak SidebarView.swift} and wire the switch statement in
          \texttt{App/\allowbreak RootView.swift}.
\end{enumerate}
